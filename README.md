# GitStream

Explore the flow of Git history. A responsive, read-only GitHub commit DAG viewer, built with React, TypeScript, Vite and Canvas 2D. No backend or database.

## Development

Node.js 22+ and npm are recommended.

```sh
npm ci
npm run dev
npm test
npm run build
```

Deploy `dist/` to any static host. Repository selection uses `?repo=owner%2Frepo` and survives refresh without server rewrites.

The bottom of Options shows the running app's build time right-aligned with a `Built at` prefix, using the browser's local date format and time zone with a consistent 24-hour `HH:mm` time. Vite embeds one UTC timestamp at build time; every device displays that same instant with its local date and zero-padded 24-hour time, without AM/PM, seconds or a time zone label. It stays fixed offline or across reloads of the same build, and the menu expands within the available viewport to keep it on one line. Unusually long values use an ellipsis, with the full localized timestamp available in the time element’s tooltip. A cached PWA keeps its previous build time until an app update is applied. Rebuilding the same commit changes the timestamp and bundle hash, so it can trigger a PWA update. The development server shows `Development`.

## Use

Enter `owner/repo` or `https://github.com/owner/repo`. The graph fills the viewport. Its transparent toolbar uses a compact repository field with an inline clear control and a search icon. Clearing edits the address and keeps loaded history. Choose a **Branch**: its first-parent history forms the straight main line, while other histories use side lanes connected by actual parent SHAs. Merged ancestry is not flattened onto the base line; unrelated histories remain separate. `main` is preferred, then `master` if `main` is absent, then the repository default. History starts at the selected branch only. In newest-first mode, visible gaps fetch ancestry from their actual parent SHAs, including merge parents with no surviving branch name. Branch names never decide which histories to fetch. In oldest-first mode, the API’s last-page link finds the oldest history directly, then scrolling down loads preceding API pages toward newer commits under a pinned head SHA. Both modes scroll down in their chosen direction. Actual roots and already loaded joins do not trigger requests. Branch-name pages serve the picker and labels only. Repository activity, including PR merges and merge queues, discovers independent branches such as active release branches, even when they have not merged into the base. Their histories enter only within the selected timeline’s date window, ordered by activity time rather than branch names. Activity pagination follows GitHub’s opaque `after` cursor; it never increments a numeric page or repeats a cursor. Empty date-filtered histories are reconsidered when exploration reaches older dates. In oldest-first mode, current active heads enter after the base traversal reaches the present. Dormant branches with no activity in the API’s last-year window remain available by selecting them explicitly. Loading stops at the history boundary or an API error; use Retry after an error. Loaded history is a partial view of the selected branch and discovered active branches until traversal ends. Dashed edges indicate unloaded parents. Compact, borderless badges use unique path suffixes and tinted branch-color backgrounds; shared anchors show a name plus a count. Full names remain in picker choices and hover tooltips. Branch-name badges follow the visible first-parent path near its line while scrolling, and disappear when that path leaves the viewport. Merge connectors and visible curve crossings also carry their branch names; nearby badges move apart to avoid covering each other. Already assigned node, branch, and edge colors remain stable when late references or ancestry arrive. Side-branch names stop at a join into another path, while references already sharing the base follow that shared history. Hover a node for a tooltip, or tap/click it for a dismissible detail panel. Select a commit node to open the compact detail panel. Options contains theme and common refresh settings. The short SHA and right-aligned authored timestamp share one row; the message ends with a small muted `by author`, with a GitHub icon beside Close. Field headings, parents, and the commit selector are omitted. The mobile commit-status panel uses only its content width. Time direction has a top-bar toggle labeled **↓ Older** or **↓ Newer**, describing the history below; its arrow always points down; theme remains under Options. Loading uses a circular spinner with an active GitHub request count such as `x5`, excluding queued work. Rotation has slow (1–4), medium (5–8), and fast (9+) speeds; reduced-motion mode keeps the count visible without rotation. The Token panel explains repository selection and required permissions before opening GitHub’s token form. Graphs keep 100% viewport width by reducing lane spacing as branch count grows. On desktop, branch lanes and badges use their natural width up to 50% of the viewport. Messages, SHAs and authors start immediately beside them and are independently capped at 50% of the viewport, with ellipses and full text available in details. Mobile keeps branches within half the screen and shows a one-line commit message beside the graph, capped at 50% of the viewport with ellipses. Tap a node or message for full details; SHAs and authors remain in the detail panel.

The base-branch picker recommends up to 30 currently existing branches. `main`, `master`, and the repository default are pinned first in that order, without duplicates; the rest rank by PRs merged into each branch in the last 90 days. PR counting starts only when the picker opens and processes up to three pages per batch. Partial counts are labeled with `+`; **Continue PR ranking** completes further batches. Deleted branches are excluded. Search filters loaded names; **Find exact branch** can select any branch outside the recommendations.

For private repositories, supply a fine-grained PAT limited to selected repositories with **Contents: Read-only**. PR recommendations additionally require **Pull requests: Read-only**. Applying it saves it in this browser’s localStorage and restores it after refresh. It is sent only to `api.github.com`. Removing it deletes the saved token and clears displayed history. Storage failures are shown in the token panel; no analytics. Public repositories work without a token, normally at 60 REST requests per hour per IP. Authenticated requests normally allow 5,000 per hour. A rate-limit error displays its retry time and pauses retries until then; permission errors are reported separately. PR-ranking failures do not clear the graph. GitHub limits can vary by authentication and secondary limits.

## Architecture and limits

`model.ts` owns data and topological lane layout; `api.ts` owns paginated REST requests; `history.ts` coordinates cancellation, encountered-parent traversal, directional pagination, deduplication, and bounded loading batches; `Graph.tsx` draws viewport nodes and intersecting edges on a DPR-aware canvas. Branch refs and lanes are separate. Commit identity is deduplicated by SHA. Parent relationships, rather than dates, determine order. Parent lanes are reused where possible, with earlier assignments preferred as pages arrive. `graphColors.ts` keeps path colors separate from lane placement: first-parent continuations and incoming merge connectors keep their path color across pagination. `branchLabels.ts` anchors labels to visible curve segments rather than only branch heads.

The canvas bounds its drawing to the viewport, but layout and edge traversal still process loaded history. No claim of unlimited history: 10,000 synthetic commits are covered by automated tests; live large-repository and 100,000-commit performance still need measurement. New history pages are requested only from unresolved boundaries currently visible below the toolbar and above the footer. Older viewport ranges and inserted offscreen rows do not trigger new requests; scrolling back to a gap re-evaluates it. Latest-follow animations do not fetch from transient viewport positions. Up to sixteen commit HTTP requests run concurrently across parent paths and activity-discovered branches. A slow branch never blocks another available slot; loading continues to accept new visible boundaries, and queued work survives scrolling out of view. Identical in-flight commit queries share one request. Accepted boundary work is registered before subscribers run, and cleanup publishes the remaining queue so unresolved cursors are reconsidered without another scroll event. Empty or mismatched boundary responses keep the gap unresolved and expose Retry rather than falsely marking the path complete. Repository, direction, or token changes cancel queued and in-flight work. Fully loaded shared ancestry is not fetched again just because an API source still has additional pages. Branch-name discovery never starts commit requests. Activity discovery scans at most one metadata page and three independent histories per batch, skips already loaded heads, and pauses with a Retry branches control if it fails. Oldest-first uses API pagination metadata to avoid downloading the complete history before rendering; if last-page metadata is unavailable, it reports an error instead of scanning every page. Errors pause new automatic loading while already accepted independent requests can finish; Retry repeats failed sources without refetching successful paths. Infinite scroll is incremental loading, not an unlimited memory or performance guarantee. No offline Git history cache; private history remains visible in memory until cleared or refreshed. GitHub access depends on the browser network policy and API quota.

## Deploy to Vercel

The repository includes `vercel.json`. Use Node.js **24.x**, framework **Vite**, install command `npm ci --no-audit --no-fund`, build command `npm run build`, and output directory `dist`. No backend, functions, environment variables, or build-time GitHub token are required. Never add a PAT as a `VITE_*` variable: those values would be public in the browser bundle.

### Git integration

The existing Vercel project `git-stream` is linked to `han41858/git-stream`. Keep the repository root as Root Directory, the Framework Preset as **Vite**, automatic Git deployments enabled, and the Production Branch as **main**. The GitHub default branch remains **dev**.

`vercel.json` explicitly enables Git deployments with `git.deploymentEnabled: true`. Keep Vercel's Preview Deployments enabled (`previewDeploymentsDisabled: false`). The separate `gitProviderOptions.createDeployments` option controls GitHub deployment records and is not the Vercel build switch.

- Feature branches (`feature/*` and existing `feat/*`) and `dev` receive Preview deployments through Vercel Git Integration.
- Merging a PR into `main` starts the Production build and deployment. Main requires a PR; its source branch is not restricted to `dev`.
- `.github/workflows/ci.yml` runs `npm ci`, `npm test`, and `npm run build` on PRs targeting `dev` or `main`, and on pushes to those branches. It reads Node.js from `.nvmrc`, caches npm downloads, and needs no additional Secrets.
- The required GitHub Actions check is **Test and build**. The Ruleset definitions in `.github/rulesets/` retain the existing protections and add this check with an up-to-date branch requirement. These JSON files are definitions; changing them in Git does not update GitHub's active Rulesets automatically.
- GitHub Actions performs validation; Vercel Git Integration performs deployment. Preview builds can run alongside CI. Main's PR checks gate merging; gating production-domain assignment on post-merge checks would require separate Vercel Deployment Checks.

Use the Git deployment as the normal release path. A manual CLI deployment is an explicit exception: it can create another deployment for the same SHA, and uncommitted files can differ from that SHA. Do not add a Vercel CLI deployment step or Vercel credentials to the CI workflow.

Verify public Production access at the project's assigned production domain using an anonymous browser session or an HTTP request without Vercel authentication. Check for HTTP 200, no login redirect, working JS/CSS, and a public repository graph. A protected generated deployment URL or an authenticated fetch does not establish anonymous access.

### Production releases

After a successful Vercel Production deployment, `.github/workflows/release.yml` creates a `rel-YYYYMMDDHHmmss` tag and GitHub Release on the **deployed commit**. The timestamp uses the verified success time in **Asia/Seoul**. Release notes contain the changes, commit, production URL, and deployment links. Preview and failed deployments do not publish releases.

Vercel's GitHub deployment records must be enabled (`gitProviderOptions.createDeployments: enabled`) so GitHub receives `deployment_status` events. This records deployments; Vercel Git Integration still performs the builds. Repository-dispatch events can stay disabled. No additional Secrets or deployment CLI are needed; only the publishing job receives `contents: write`.

The workflow verifies the persisted GitHub deployment and status from the Vercel bot, the team/project dashboard URL, and that the deployed SHA belongs to `main`. Automation code is checked out from the protected default branch, not from the event's deployed commit. Runs for the same SHA are serialized. Repeated events and redeployments reuse the commit's release; failed publication reuses its tag on retry. Existing tags are never moved. A timestamp collision with another commit uses the next free second, and delayed events do not replace a newer Latest release.

To verify or recover a missed event, run **Production release** from the default branch with its **GitHub deployment ID**. Dry run is enabled by default and writes no tag or release; disable it only to publish the verified successful Production deployment. Preview IDs are safe to test and are skipped. Existing historical deployments are not backfilled automatically.

The workflow and scripts must be on `main` before its next Production deployment. Keep the protected default branch (`dev`) up to date as well, since it supplies the trusted automation code. Publication uses the exact automation commit verified by the inspection job. The CI job also runs `node --test --test-isolation=none .github/scripts/*.test.mjs`.

### Before publishing

```sh
npm ci --no-audit --no-fund
npm test
npm run build
npm run preview -- --port 4173
```

On the deployment, open a public repository such as `han41858/git-stream` and `angular/angular`; verify real commit data, branch selection, loading older history, direction reversal, commit links, and refreshing a `?repo=owner%2Frepo` URL. Test mobile tapping and fixed-width vertical scrolling, and desktop content-sized graph columns capped at 50% and messages capped at 50%. A fine-grained PAT can be entered in the app for a private-repository check; remove it afterwards and confirm the history clears. Check invalid repository and API-limit messages.

The current cloud environment's `api.github.com` egress policy is separate from Vercel. API requests originate in the visitor's browser. Unit tests and mocked browser checks do not establish that live GitHub access works; live API and private-repository validation remain release checks.

Hashed Vite assets use immutable caching; the HTML keeps Vercel's default caching. Security headers disable framing and sensitive device permissions, prevent MIME sniffing, and omit the referrer. A Content Security Policy allows scripts and PWA shell requests from this site and GitHub API requests to `api.github.com`, so a stored token cannot be sent elsewhere by injected code. Query-based navigation does not require a catch-all rewrite.

Vercel GitHub bot comments are disabled through the project’s commit/PR comment settings and `github.silent` in `vercel.json`.

Month separators span the viewport with `YYYY.MM` above the line at the right. They attach to the earliest commit near the first of each month in both directions. A partial oldest month waits for older context instead of being labeled at the month end.


## Automatic updates and metadata

In newest-first mode, a reader at the latest edge follows newer commits arriving from independent branch discovery as well as refreshes. A short eased scroll reveals new commits, continues across overlapping branch responses, stops on direct scroll input, and respects reduced motion. Reading older history keeps the current commit anchored; older pagination and unchanged metadata do not snap the viewport. The refresh button updates the current repository. Options provides a single automatic refresh switch and interval (authenticated: 30 seconds, 1 minute or 5 minutes; anonymous: 1 or 5 minutes). Defaults are 1 minute with an applied token and 5 minutes without. Hidden/offline tabs pause; overdue updates resume on return. The footer shows the last successful refresh or its error/backoff state.

Tags (🏷️), GitHub Releases (🚀) and Actions rings augment commits without changing their coordinates. Select a commit for version links, consistent 16px outline SVG workflow status icons beside their names (green check, yellow spinner, gray waiting clock, red failure/timeout, and distinct cancel/skip/warning/unknown shapes), elapsed duration, attempts and known job counts. Active durations update locally; completed durations freeze at the final API status update without additional requests. Active workflow rows show completed/total job counts between the name and status icon; unconfirmed counts show ?/?, and completed workflows omit the count. The Actions heading shows a compact yellow completed/total summary such as 48/51 jobs (94%), without a separate status line or progress bar, alongside total elapsed time from the earliest workflow start to now or the final run status update when all runs finish. Overlapping workflows share elapsed wall time. Percentages count completed jobs, not elapsed time; incomplete or unconfirmed totals use a rotating graph donut without a percentage. Rotation is limited to visible running commits, pauses in hidden tabs, respects reduced motion and adds no API calls or canvas redraw loop. A Release icon does not mean a deployment completed. Actions access optionally needs **Actions: Read-only**. Missing metadata permissions do not clear the graph.

The Token popup maps features to required read permissions and checks the applied token against the selected repository. It validates token identity, then probes Contents, Pull requests and Actions separately; Recheck repeats the checks. Edited tokens are checked after Apply, and results are not persisted. ✅ marks available access, 🚫 marks blocked access or an invalid token, and unverified/rate-limited states remain distinct. The popup omits login IDs and repeated repository labels. Checks report repository feature access rather than the complete token grant list. Create token is a prominent button and closes the token popup when opening GitHub. Opening the token popup dismisses prior API-limit guidance without clearing the retry deadline. Token, Options, branch and commit-detail popups close on outside presses or Escape; interaction inside a popup keeps it open. Closing commit details also clears the selection and restores the node and Actions ring to their usual sizes, while keeping fetched metadata cached.

Conditional ETag reads reuse unchanged data. Known commits are reused. For a commit with active workflows, missing completed-job snapshots are filled once so aggregate progress has every denominator; complete final snapshots are cached. Finished commits stop job reads, while recent workflow runs can reactivate tracking on a new attempt. Reference deletion requires a complete branch catalog. Unreachable commits are removed only when ancestry can be established; partial history is retained without a separate footer notice. Tag and release names share rows with their icons, and matching release names/versions are shown once. Version/run history is loaded in bounded pages: scrolling the commit panel continues version catalogs, the selected SHA’s runs and unfinished job pages. A short panel loads one initial continuation; further pages follow wheel, touch or keyboard scrolling without a button or repeated completed-page requests. See [the extension specification](docs/auto-refresh-and-metadata.md).

## Developer diagnostics

In development, press **Ctrl + Shift + D** to open the debug panel. On any build, use `/?repo=owner%2Frepository&debug=1` to enable the small debug entry button. Closing the panel keeps measurements running; **Disable debug** stops and clears them.

In the installed PWA, enter `:debug` in the existing repository field and press Enter or Explore. This also works on the web. It opens diagnostics and restores the current repository field without reloading the page, changing the URL, or issuing API requests. It keeps existing measurements if already enabled; otherwise it starts a new in-memory debug session. No debug button is shown by default, and the command needs to be entered again after a fresh launch or reload unless `?debug=1` is present.

The panel separates HTTP/cache/quota observations, initial/manual/automatic refreshes, DAG layout and Canvas drawing. Each category retains its latest 20 samples in memory. **Copy diagnostics** exports numeric, sanitized JSON; details and refresh summaries also appear in DevTools Console. No extra API calls, external telemetry or persisted diagnostics are added. See [the developer debug specification](docs/developer-debug-mode.md) for measurement boundaries and limitations.

## Installable web app (PWA)

GitStream can be installed from a supported browser or added to the iOS home screen. It opens in standalone mode with the existing graph and controls. No install banner is shown. The app identity and launcher start at `/`; repository links still use `?repo=`.

Production builds use `vite-plugin-pwa` to cache the static app shell, including lazy UI assets. **GitHub API responses, private history and PATs are never stored in Service Worker Cache Storage.** GitHub still needs a network connection. The existing browser localStorage token policy is unchanged. Service Workers require HTTPS (localhost works for development verification); Vite's dev server does not register the production worker.

A ready app version shows **Update app** and **Later**. Applying reloads the consenting window after the new worker activates, preserving its URL. Another tab's approval does not force the current tab to reload. Failed downloads leave the installed shell available. Static cache cleanup happens on activation. Preview and Production have separate origins, workers, caches and installations; use the stable Production domain for normal installation.

See [the PWA specification and verification checklist](docs/pwa.md) for cache boundaries, update behavior, CSP changes and physical-device checks that still need a release environment.
