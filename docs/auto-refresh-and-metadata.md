# GitStream — 자동 갱신 및 커밋 메타데이터 확장 명세서

## 1. 개요

GitStream에 GitHub 저장소의 변경 사항을 자동으로 감지하고 그래프에 반영하는 기능을 추가합니다.

아울러 Git 태그, GitHub Release, GitHub Actions 실행 상태를 각 커밋에 연결하여 표시합니다.

AI 코딩 에이전트나 GitHub Actions가 작업하는 동안 GitStream을 열어두면, 커밋과 브랜치의 변화뿐 아니라 자동화 작업의 진행 상황도 확인할 수 있도록 합니다.

### 기본 원칙

- 기존 GitStream의 세로형 Git DAG 시각화 유지
- GitHub REST API 기반 Polling 사용
- 별도 백엔드, WebSocket, Webhook 불필요
- 변경된 데이터만 필요한 범위에서 조회
- 기존 그래프의 위치와 사용자 탐색 상태 최대한 유지
- 커밋의 메타데이터 변경은 DAG 구조에 영향 없음
- 읽기 전용 정책 유지
- 불필요한 설정과 의존성 추가 금지

## 2. 자동 갱신 설정

### 2.1 UI

기존 그래프 화면에 간단한 자동 갱신 컨트롤을 제공합니다.

- 자동 갱신 ON/OFF
- 갱신 주기 선택
- 수동 새로고침
- 마지막 정상 갱신 시각 표시
- 갱신 중 또는 오류 상태 표시

별도의 복잡한 설정 화면은 만들지 않습니다.

### 2.2 갱신 주기

| 구분 | 기본 주기 |
|---|---|
| PAT 인증 사용자 | 1분 |
| 비인증 사용자 | 5분 |
| 수동 새로고침 | 즉시 |

선택 가능한 주기는 30초, 1분, 5분입니다.

비인증 사용자에게는 30초 주기를 제공하지 않습니다.

자동 갱신은 기본적으로 활성화하며 사용자가 비활성화할 수 있습니다.

갱신 설정은 현재 앱 세션에서 유지합니다. 토큰은 사용자가 확인한 기존 방침에 따라 localStorage 저장을 유지합니다.

갱신 주기는 브랜치, 커밋, 태그, 릴리즈, Actions에 공통으로 적용합니다.

기능별로 별도의 갱신 주기 설정을 추가하지 않습니다.

다만 실제 API 요청은 데이터 특성과 캐시 상태에 따라 필요한 경우에만 실행할 수 있습니다.

### 2.3 실행 조건

| 상황 | 동작 |
|---|---|
| 활성 탭 | 지정한 주기로 갱신 |
| 백그라운드 탭 | 자동 갱신 일시 중지 |
| 탭 복귀 | 마지막 갱신 이후 설정 주기가 지났다면 갱신 |
| 네트워크 오프라인 | 갱신 중지 |
| 네트워크 복구 | 갱신 재개 |
| 저장소 변경 | 이전 요청 취소 후 새 저장소 조회 |
| 자동 갱신 OFF | 주기적 요청 중지 |
| 수동 새로고침 | 현재 저장소 즉시 갱신 |

동일한 저장소에 대한 갱신이 중복 실행되지 않도록 합니다.

진행 중인 갱신이 있을 때 다음 실행 시점이 도달하면 중복 요청을 생성하지 않습니다.

수동 갱신이 완료되면 다음 자동 갱신 시점을 다시 계산합니다.

## 3. 커밋·브랜치 자동 갱신

### 3.1 브랜치 변경 감지

GitHub Branches API를 사용하여 현재 브랜치 목록과 HEAD SHA를 확인합니다.

이전 조회 결과와 비교하여 다음 변경을 감지합니다.

| 변경 유형 | 처리 |
|---|---|
| 변경 없음 | 기존 그래프 유지 |
| 브랜치 생성 | 새로운 브랜치 참조 추가 |
| 브랜치 삭제 | 기존 브랜치 참조 제거 |
| HEAD SHA 변경 | 해당 브랜치의 커밋 이력 갱신 |
| 기본 브랜치 변경 | 기본 브랜치 표시 갱신 |

브랜치 목록은 페이지네이션을 고려합니다.

일부 페이지만 조회한 상태에서 브랜치가 삭제되었다고 판단해서는 안 됩니다.

브랜치 목록 조회에 실패하면 기존 상태를 유지하고 이후 갱신에서 재시도합니다.

### 3.2 커밋 증분 조회

HEAD SHA가 변경된 브랜치는 필요한 커밋 이력을 추가 조회합니다.

- 새로운 HEAD SHA 확인
- 기존에 알고 있는 커밋까지 필요한 이력 탐색
- 신규 커밋을 SHA 기준으로 추가
- 기존 커밋과 중복 제거
- 부모 SHA 관계 갱신
- 필요한 그래프 영역 재계산

기존 커밋 데이터는 재사용합니다.

브랜치 HEAD가 변경되었다는 이유만으로 전체 저장소 이력을 다시 다운로드하지 않습니다.

여러 브랜치에서 동일한 신규 커밋이 발견되면 하나의 커밋으로 관리합니다.

### 3.3 Force Push 및 Rebase

HEAD 변경이 단순한 커밋 추가가 아닐 수 있습니다.

Force Push, Rebase, Reset 등으로 기존 이력이 변경된 경우를 처리해야 합니다.

- 새로운 HEAD에서 접근 가능한 이력 확인
- 기존 커밋과의 공통 조상 확인
- 해당 브랜치의 참조 및 경로 갱신
- 더 이상 해당 브랜치에서 접근할 수 없는 커밋의 연결 상태 재평가
- 다른 브랜치에서 접근 가능한 커밋은 유지

브랜치가 삭제되거나 이력이 변경되었다고 해서 모든 관련 커밋을 무조건 삭제하지 않습니다.

부분 조회로 관계를 확정할 수 없는 경우 불완전한 데이터임을 표시합니다.

### 3.4 부분 데이터 처리

대형 저장소에서는 전체 이력을 메모리에 보유하지 않을 수 있습니다.

따라서 다음 원칙을 유지합니다.

- 조회하지 않은 부모 커밋은 미조회 상태로 관리
- 없는 커밋과 아직 조회하지 않은 커밋을 구분
- 그래프의 연결 경계를 정확히 표시
- 추가 데이터가 들어와도 기존 레인의 불필요한 이동 최소화
- 이전에 조회한 SHA 및 페이지 결과 재사용

## 5. Git 태그 표시

### 5.1 UI

태그가 연결된 커밋 옆에 🏷️ 아이콘을 표시합니다.

- 동일 커밋에 여러 태그가 있어도 아이콘은 하나
- Hover 또는 Tap으로 태그 이름 표시
- 태그 선택 시 GitHub 원본 페이지 이동
- 태그가 없는 커밋은 기존 모습 유지

태그 아이콘은 커밋 원형 노드와 구분하여 표시합니다.

### 5.2 데이터 처리

GitHub REST API에서 태그 정보를 조회합니다.

- Lightweight Tag 지원
- Annotated Tag 지원
- Annotated Tag는 최종 대상 커밋 SHA 확인
- SHA 기준으로 커밋 연결
- 페이지네이션 처리
- 중복 데이터 제거

현재 조회 범위에 없는 태그를 근거로 해당 커밋에 태그가 없다고 확정하지 않습니다.

## 6. GitHub Release 표시

### 6.1 UI

GitHub Release가 연결된 커밋 옆에 🚀 아이콘을 표시합니다.

- Release가 없는 커밋은 표시하지 않음
- 태그와 Release가 모두 존재하면 🏷️🚀 함께 표시
- Hover 또는 Tap 시 Release 상세 정보 표시
- Release 이름, 버전, 게시 시각, GitHub 링크 제공
- Pre-release 여부 구분

하나의 커밋에 여러 Release가 연결된 경우에도 로켓 아이콘은 하나만 표시하고 상세 정보에 목록을 제공합니다.

### 6.2 데이터 처리

GitHub Releases API를 사용합니다.

- Release와 연결된 태그 확인
- 해당 태그가 가리키는 최종 커밋 SHA 확인
- SHA 기준으로 그래프에 연결
- 페이지네이션 지원
- 접근 가능한 Draft Release 처리

### 6.3 의미 구분

🚀 아이콘은 **GitHub Release가 존재한다는 의미**입니다.

실제 운영 환경에 배포되었다는 의미가 아닙니다.

GitHub Deployments API를 통한 실제 배포 상태 추적은 이번 범위에서 제외합니다.

## 7. GitHub Actions 상태 표시

### 7.1 기본 표현

Actions 실행 정보가 있는 커밋은 기존 원형 노드에 상태 링을 추가합니다.

| 상태 | 표현 |
|---|---|
| Actions 정보 없음 | 기존 원형 점 |
| 대기 중 | 회색 링 |
| 실행 중 | 노란색 진행률 링 |
| 모두 성공 | 초록색 완료 링 |
| 실패 | 빨간색 완료 링 |
| 취소 | 회색 완료 링 |
| 기타 결과 | 중립 상태 링 |

기존 커밋의 중심점과 브랜치 레인 색상은 유지합니다.

링은 중심점 주변을 도넛형으로 둘러싸는 형태로 구현합니다.

커밋의 크기나 그래프 레인 간격이 불필요하게 커지지 않도록 합니다.

### 7.2 여러 워크플로 합산

하나의 커밋에서 여러 워크플로가 실행되면 진행률을 합산합니다.

계산식:

**진행률 = 완료된 Job 수 / 전체 Job 수 × 100**

예시:

| 워크플로 | 전체 Job | 완료 Job |
|---|---:|---:|
| Build | 3 | 3 |
| Test | 4 | 2 |
| Deploy | 3 | 0 |
| 합계 | 10 | 5 |

이 경우 커밋 노드에는 50% 진행률을 표시합니다.

진행률은 전체 작업 시간 기준이 아니라 **Job 완료 개수 기준**입니다.

### 7.3 진행률 계산 규칙

- 성공·실패·취소·건너뜀으로 종료된 Job은 완료 개수에 포함
- 실행 중 또는 대기 중인 Job은 완료 개수에서 제외
- 동일한 Job 중복 집계 금지
- 여러 워크플로의 Job을 합산
- Job 목록이 미확정이면 퍼센트 없이 회전하는 도넛으로 진행 중 상태 표시. 개수가 확인되면 실제 완료 비율을 표시하며, 완료되지 않은 실행을 성공으로 처리하지 않음
- Matrix Job 등으로 분모가 바뀔 수 있음을 고려
- 진행률을 임의로 증가시키지 않음

모든 Job이 종료되어 완료율이 100%가 되더라도 GitHub가 최종 실행 결과를 확정하기 전에는 성공으로 표시하지 않습니다.

### 7.4 최종 상태

모든 워크플로가 종료되면 진행률 대신 최종 상태를 표시합니다.

대표 상태 판단 규칙:

1. 대기 중이거나 실행 중인 워크플로가 있으면 진행 중
2. 모두 종료되었고 하나라도 실패 또는 시간 초과가 있으면 실패
3. 모두 성공했다면 성공
4. 취소, 건너뜀, 중립 결과가 섞인 경우 별도 중립 상태

GitHub API의 `status`와 `conclusion`을 구분합니다.

알 수 없는 상태를 임의로 성공 또는 실패로 분류하지 않습니다.

### 7.5 재실행

GitHub Actions는 완료된 워크플로를 재실행할 수 있습니다.

- Workflow Run은 `run_id`로 식별
- 동일 실행의 여러 시도를 중복 집계하지 않음
- 최신 `run_attempt` 기준으로 상태 처리
- 재실행 시 기존 완료 상태를 다시 진행 중으로 변경 가능
- 최신 시도의 Job을 기준으로 진행률 계산

한 번 완료된 실행을 영구적으로 변경되지 않는 데이터로 취급하지 않습니다.

다만 일반적인 완료 상태의 상세 Job 정보는 반복 조회하지 않고 캐시를 재사용할 수 있습니다.

### 7.6 Actions 상세 정보

커밋을 Hover 또는 Tap하면 연결된 워크플로 정보를 표시합니다.

- 워크플로 이름
- 이름 옆 배경 없는 16px SVG 상태 아이콘으로 최종 결과 표시. 완료 상태 텍스트를 별도로 반복하지 않음
- 진행 중인 실행은 이름과 상태 아이콘 사이에 완료된 Job 수 / 전체 Job 수 표시. 미확정이면 `?/?`, 완료된 실행은 개수 생략
- 경과 시간: 진행 중에는 갱신하고 완료 후에는 고정
- 실행 시도
- GitHub Actions 실행 링크

기존 커밋 상세 정보 UI에 통합합니다.

Actions 전용 대시보드는 만들지 않습니다.

## 8. Actions 데이터 조회

### 8.1 최근 Workflow Runs 일괄 조회

커밋마다 개별 API를 호출하는 대신 저장소의 최근 Workflow Runs를 일괄 조회합니다.

기본 처리 순서:

1. 최근 Workflow Runs 조회
2. 필요한 페이지 추가 조회
3. `head_sha` 기준으로 커밋과 연결
4. 동일한 `run_id` 중복 제거
5. 최신 실행 시도 확인
6. 진행 상태 계산에 필요한 Job 정보 조회
7. 커밋별 전체 진행률 및 대표 상태 계산
8. 기존 그래프 노드에 반영

최근 실행과 현재 표시 중인 커밋을 우선 처리합니다.

대형 저장소에서 전체 Actions 이력을 다운로드하지 않습니다.

### 8.2 과거 커밋

최근 Workflow Runs에 나타나지 않는 과거 커밋에도 Actions 실행 이력이 있을 수 있습니다.

- 최근 조회 결과에 없는 커밋은 기본 원형 노드로 표시
- 해당 커밋에 Actions가 없다고 확정하지 않음
- 사용자가 커밋을 선택하면 필요한 경우 `head_sha` 기반 추가 조회
- 결과는 메모리 캐시에 보관

GitHub의 실행 이력 보존 정책에 따라 오래된 정보는 확인하지 못할 수 있습니다.

### 8.3 커밋 연결 정확성

워크플로 실행의 `head_sha`를 기준으로 연결합니다.

PR 임시 병합 커밋과 같이 실행 대상 SHA가 그래프의 커밋 SHA와 다른 경우가 있습니다.

- 일치하는 SHA에만 기본적으로 연결
- 일치하지 않는 실행을 추측으로 연결하지 않음
- GitHub가 반환한 실제 실행 대상 정보 우선
- 하나의 커밋에 여러 실행이 연결되는 경우 모두 고려

외부 CI 서비스와 GitHub Checks API의 추가 연동은 이번 범위에서 제외합니다.

## 9. 공통 자동 갱신

커밋·브랜치·태그·릴리즈·Actions는 동일한 자동 갱신 스케줄을 사용합니다.

한 번의 갱신 주기에서 필요한 데이터 변경 여부를 확인합니다.

단, 모든 API를 매번 무조건 호출하는 구조는 피합니다.

### 9.1 데이터별 갱신

| 데이터 | 처리 |
|---|---|
| 브랜치 | HEAD SHA 및 목록 변화 확인 |
| 커밋 | 변경된 브랜치의 이력 증분 조회 |
| 태그 | 새 태그 및 변경된 참조 확인 |
| 릴리즈 | 새 릴리즈 및 변경된 정보 확인 |
| Actions | 최근 Workflow Runs 및 진행 중 상태 확인 |

Actions는 커밋 SHA가 변경되지 않아도 상태가 변경될 수 있으므로 별도로 변경 여부를 확인해야 합니다.

태그와 릴리즈도 커밋 변경 없이 추가될 수 있습니다.

### 9.2 변경된 정보만 반영

- 커밋 구조가 변하면 필요한 DAG 레이아웃 갱신
- 태그·릴리즈만 변하면 해당 아이콘 갱신
- Actions 상태만 변하면 해당 원형 노드 갱신
- 변경이 없으면 기존 그래프 유지
- 화면 전체 재구성 및 불필요한 스크롤 이동 금지

### 9.3 API 호출 효율화

- 가능한 경우 ETag 및 `If-None-Match` 사용
- 중복 API 요청 방지
- 기존 SHA 데이터 재사용
- 최근 실행 및 진행 중 상태 우선
- 완료된 Job 정보 캐시
- 페이지네이션 및 조회 범위 제한
- Rate Limit 헤더 확인

GitHub API의 기본 요청 제한뿐 아니라 보조 요청 제한도 고려합니다.

Rate Limit에 도달하면 자동 갱신을 중단하고, 해제 시각 또는 재시도 가능 시각을 기준으로 재개합니다.

오류 상황에서 과도한 재요청을 하지 않습니다.

## 17. 구현 범위와 캐시 정책

- 하나의 갱신 루프를 사용하며, 수동 갱신과 주기 갱신은 중복 실행하지 않습니다. 숨김 탭·오프라인에서는 일시 중지하고 Rate Limit의 재시도 시각을 따릅니다.
- 브랜치 목록은 한 주기에 최대 3페이지씩 이어서 확인합니다. 전체 목록을 확인하기 전에는 삭제를 확정하지 않습니다. 삭제된 참조의 HEAD 추적은 종료하고, 공유 커밋과 관계를 확정하지 못한 기존 이력은 유지합니다.
- 이미 받은 커밋 객체와 고정 SHA의 조회 페이지를 재사용합니다. 메타데이터만 바뀌면 DAG 레이아웃과 스크롤 좌표를 유지합니다.
- 태그·릴리즈·최근 실행 목록은 페이지당 최대 100개입니다. 태그·릴리즈는 이미 열어 본 목록 페이지를 조건부로 재확인하고, 추가 페이지는 커밋 상세 팝업의 하단 스크롤로 이어서 요청합니다. 짧은 팝업은 최초 한 배치만 자동으로 채우고 이후 휠·터치·키보드의 아래 방향 탐색에 따라 진행합니다. 변경 없는 상세와 Annotated Tag 객체는 캐시를 재사용합니다.
- 최근 실행 목록 밖으로 밀려난 진행 중 실행도 최종 상태까지 확인합니다. 완료된 실행의 Job은 반복 조회하지 않으며, 최근 목록에서 새 실행이나 `run_attempt` 변경이 발견되면 다시 추적합니다.
- 경과 시간은 기존 실행의 `run_started_at`부터 계산하며 완료된 실행은 마지막 API 상태 갱신 시각인 `updated_at`을 종료 기준으로 사용합니다. 시각이 누락되거나 잘못된 경우 `—`로 표시합니다. 진행 중인 상세 화면에서만 로컬 시계를 갱신하며 추가 API 요청을 보내지 않습니다.
- Job 조회는 선택한 커밋과 화면에 보이는 최대 24개 커밋을 우선합니다. 한 실행의 Job 페이지는 최대 5페이지씩 이어서 확인하며, 목록과 분모가 확정되지 않으면 비율을 표시하지 않습니다. 같은 커밋에 진행 중인 실행이 있으면 합산 분모에 필요한 완료 실행의 Job도 한 번 채워 캐시합니다. 완료 전환 당시 남아 있던 진행 중 Job 정보는 최종 스냅샷으로 보정하며, 확정된 완료 캐시는 반복 조회하지 않습니다. 전체 실행이 종료된 커밋은 Job을 추가 조회하지 않고 최종 상태를 유지합니다. 조회 실패나 미완료 페이지를 임의의 진행률로 바꾸지 않습니다.
- 선택한 과거 SHA의 실행은 최대 3페이지씩 확인하고 스크롤로 이어갑니다. 이미 받은 커밋의 첫 페이지나 무관한 저장소 전체 실행 이력을 추가로 훑지 않습니다. 완료한 목록은 다시 요청하지 않으며, 진행 중인 실행의 미완료 Job 페이지도 이어받습니다. PR 임시 병합 SHA는 다른 SHA의 커밋에 연결하지 않습니다.
- 조회 실패와 부분 페이지는 삭제나 데이터 부재의 증거로 사용하지 않습니다. 토큰의 localStorage 저장은 사용자가 확인한 기존 정책을 유지합니다.
- 캐시는 현재 저장소·토큰 세션의 메모리에만 유지합니다. 실제 대규모 저장소의 장시간 실측과 API 요청 횟수 계측은 이번 검증 범위에 포함하지 않았습니다.

- 커밋 상세 작성자는 메시지 뒤에 기존의 작은 회색 스타일로 `by 이름`을 붙입니다. 태그·릴리즈 이름은 각 아이콘과 같은 줄에 표시하고, 릴리즈 이름과 태그 이름이 같으면 반복하지 않습니다.

- Actions 상태는 모두 배경 없는 16px SVG로 표시합니다. 성공은 초록 체크, 진행 중은 노란 회전 링, 대기는 회색 시계, 실패·시간 초과는 빨간색이며 취소·건너뜀·조치 필요·알 수 없음도 서로 다른 모양으로 구분합니다. 아이콘과 텍스트는 세로 중앙 정렬하며 동작 줄이기 설정에서는 회전을 멈춥니다.

- 커밋 상세의 Actions 제목 옆에 노란색으로 `완료/전체 jobs (정수%)`를 표시합니다. 합계가 확정된 진행·대기 상태에만 표시하며 별도의 In progress 줄·진행바·반복 설명은 생략합니다.

- Actions 제목 옆 시계 아이콘과 전체 경과 시간을 표시합니다. 같은 커밋의 최신 시도들 중 가장 이른 시작부터 현재까지 계산하고, 모든 실행 종료 시 가장 늦은 최종 상태 갱신 시각으로 고정합니다. 병렬 실행 시간은 중복 합산하지 않으며 시각이 불명확하면 총 시간을 추측하지 않습니다.
