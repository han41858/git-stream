# GitStream — 자동 갱신 및 커밋 메타데이터 확장 명세서

## 1. 개요

GitStream에 GitHub 저장소의 변경 사항을 자동으로 감지하고 그래프에 반영하는 기능을 추가합니다.

아울러 Git 태그, GitHub Release, GitHub Actions 실행 상태를 각 커밋에 연결하여 표시합니다.

AI 코딩 에이전트나 GitHub Actions가 작업하는 동안 GitStream을 열어두면, 커밋과 브랜치의 변화뿐 아니라 자동화 작업의 진행 상황도 확인할 수 있도록 합니다.

### 기본 원칙

- 기존 GitStream의 세로형 Git DAG 시각화 유지
- GitHub REST API 기반 Polling 사용
- 별도 백엔드, WebSocket, Webhook 불필요
- 변경된 데이터만 필요한 범위에서 조회
- 기존 그래프의 위치와 사용자 탐색 상태 최대한 유지
- 커밋의 메타데이터 변경은 DAG 구조에 영향 없음
- 읽기 전용 정책 유지
- 불필요한 설정과 의존성 추가 금지

## 2. 자동 갱신 설정

### 2.1 UI

기존 그래프 화면에 간단한 자동 갱신 컨트롤을 제공합니다.

- 자동 갱신 ON/OFF
- 갱신 주기 선택
- 수동 새로고침
- 마지막 정상 갱신 시각 표시
- 갱신 중 또는 오류 상태 표시

별도의 복잡한 설정 화면은 만들지 않습니다.

### 2.2 갱신 주기

| 구분 | 기본 주기 |
|---|---|
| PAT 인증 사용자 | 1분 |
| 비인증 사용자 | 5분 |
| 수동 새로고침 | 즉시 |

선택 가능한 주기는 30초, 1분, 5분입니다.

비인증 사용자에게는 30초 주기를 제공하지 않습니다.

자동 갱신은 기본적으로 활성화하며 사용자가 비활성화할 수 있습니다.

갱신 설정은 현재 앱 세션에서 유지합니다. 토큰은 사용자가 확인한 기존 방침에 따라 localStorage 저장을 유지합니다.

갱신 주기는 브랜치, 커밋, 태그, 릴리즈, Actions에 공통으로 적용합니다.

기능별로 별도의 갱신 주기 설정을 추가하지 않습니다.

다만 실제 API 요청은 데이터 특성과 캐시 상태에 따라 필요한 경우에만 실행할 수 있습니다.

### 2.3 실행 조건

| 상황 | 동작 |
|---|---|
| 활성 탭 | 지정한 주기로 갱신 |
| 백그라운드 탭 | 자동 갱신 일시 중지 |
| 탭 복귀 | 마지막 갱신 이후 설정 주기가 지났다면 갱신 |
| 네트워크 오프라인 | 갱신 중지 |
| 네트워크 복구 | 갱신 재개 |
| 저장소 변경 | 이전 요청 취소 후 새 저장소 조회 |
| 자동 갱신 OFF | 주기적 요청 중지 |
| 수동 새로고침 | 현재 저장소 즉시 갱신 |

동일한 저장소에 대한 갱신이 중복 실행되지 않도록 합니다.

진행 중인 갱신이 있을 때 다음 실행 시점이 도달하면 중복 요청을 생성하지 않습니다.

수동 갱신이 완료되면 다음 자동 갱신 시점을 다시 계산합니다.

## 3. 커밋·브랜치 자동 갱신

### 3.1 브랜치 변경 감지

GitHub Branches API를 사용하여 현재 브랜치 목록과 HEAD SHA를 확인합니다.

이전 조회 결과와 비교하여 다음 변경을 감지합니다.

| 변경 유형 | 처리 |
|---|---|
| 변경 없음 | 기존 그래프 유지 |
| 브랜치 생성 | 새로운 브랜치 참조 추가 |
| 브랜치 삭제 | 기존 브랜치 참조 제거 |
| HEAD SHA 변경 | 해당 브랜치의 커밋 이력 갱신 |
| 기본 브랜치 변경 | 기본 브랜치 표시 갱신 |

브랜치 목록은 페이지네이션을 고려합니다.

일부 페이지만 조회한 상태에서 브랜치가 삭제되었다고 판단해서는 안 됩니다.

브랜치 목록 조회에 실패하면 기존 상태를 유지하고 이후 갱신에서 재시도합니다.

### 3.2 커밋 증분 조회

HEAD SHA가 변경된 브랜치는 필요한 커밋 이력을 추가 조회합니다.

- 새로운 HEAD SHA 확인
- 기존에 알고 있는 커밋까지 필요한 이력 탐색
- 신규 커밋을 SHA 기준으로 추가
- 기존 커밋과 중복 제거
- 부모 SHA 관계 갱신
- 필요한 그래프 영역 재계산

기존 커밋 데이터는 재사용합니다.

브랜치 HEAD가 변경되었다는 이유만으로 전체 저장소 이력을 다시 다운로드하지 않습니다.

여러 브랜치에서 동일한 신규 커밋이 발견되면 하나의 커밋으로 관리합니다.

### 3.3 Force Push 및 Rebase

HEAD 변경이 단순한 커밋 추가가 아닐 수 있습니다.

Force Push, Rebase, Reset 등으로 기존 이력이 변경된 경우를 처리해야 합니다.

- 새로운 HEAD에서 접근 가능한 이력 확인
- 기존 커밋과의 공통 조상 확인
- 해당 브랜치의 참조 및 경로 갱신
- 더 이상 해당 브랜치에서 접근할 수 없는 커밋의 연결 상태 재평가
- 다른 브랜치에서 접근 가능한 커밋은 유지

브랜치가 삭제되거나 이력이 변경되었다고 해서 모든 관련 커밋을 무조건 삭제하지 않습니다.

부분 조회로 관계를 확정할 수 없는 경우 불완전한 데이터임을 표시합니다.

### 3.4 부분 데이터 처리

대형 저장소에서는 전체 이력을 메모리에 보유하지 않을 수 있습니다.

따라서 다음 원칙을 유지합니다.

- 조회하지 않은 부모 커밋은 미조회 상태로 관리
- 없는 커밋과 아직 조회하지 않은 커밋을 구분
- 그래프의 연결 경계를 정확히 표시
- 추가 데이터가 들어와도 기존 레인의 불필요한 이동 최소화
- 이전에 조회한 SHA 및 페이지 결과 재사용

## 9. 공통 자동 갱신

커밋·브랜치·태그·릴리즈·Actions는 동일한 자동 갱신 스케줄을 사용합니다.

한 번의 갱신 주기에서 필요한 데이터 변경 여부를 확인합니다.

단, 모든 API를 매번 무조건 호출하는 구조는 피합니다.

### 9.1 데이터별 갱신

| 데이터 | 처리 |
|---|---|
| 브랜치 | HEAD SHA 및 목록 변화 확인 |
| 커밋 | 변경된 브랜치의 이력 증분 조회 |
| 태그 | 새 태그 및 변경된 참조 확인 |
| 릴리즈 | 새 릴리즈 및 변경된 정보 확인 |
| Actions | 최근 Workflow Runs 및 진행 중 상태 확인 |

Actions는 커밋 SHA가 변경되지 않아도 상태가 변경될 수 있으므로 별도로 변경 여부를 확인해야 합니다.

태그와 릴리즈도 커밋 변경 없이 추가될 수 있습니다.

### 9.2 변경된 정보만 반영

- 커밋 구조가 변하면 필요한 DAG 레이아웃 갱신
- 태그·릴리즈만 변하면 해당 아이콘 갱신
- Actions 상태만 변하면 해당 원형 노드 갱신
- 변경이 없으면 기존 그래프 유지
- 화면 전체 재구성 및 불필요한 스크롤 이동 금지

### 9.3 API 호출 효율화

- 가능한 경우 ETag 및 `If-None-Match` 사용
- 중복 API 요청 방지
- 기존 SHA 데이터 재사용
- 최근 실행 및 진행 중 상태 우선
- 완료된 Job 정보 캐시
- 페이지네이션 및 조회 범위 제한
- Rate Limit 헤더 확인

GitHub API의 기본 요청 제한뿐 아니라 보조 요청 제한도 고려합니다.

Rate Limit에 도달하면 자동 갱신을 중단하고, 해제 시각 또는 재시도 가능 시각을 기준으로 재개합니다.

오류 상황에서 과도한 재요청을 하지 않습니다.

## 11. 오류 처리

자동 갱신이 실패해도 기존 그래프는 유지합니다.

구분할 오류:

- 네트워크 장애
- API Rate Limit
- 인증 토큰 만료
- 권한 부족
- 저장소 접근 불가
- 일부 브랜치 조회 실패
- Actions 조회 실패
- 태그 또는 릴리즈 조회 실패

일부 부가 정보 조회가 실패해도 전체 그래프를 초기화하지 않습니다.

마지막 정상 갱신 시각과 오류 상태를 확인할 수 있도록 합니다.

일부 페이지만 성공한 결과로 삭제나 데이터 부재를 확정하지 않습니다.

## 12. 성능

기존 Canvas 2D 렌더러와 가상 스크롤 구조를 유지합니다.

- Git DAG 데이터와 메타데이터 분리
- 메타데이터 변경은 레이아웃 재계산 없이 처리
- 화면에 표시되는 노드 중심으로 렌더링
- 완료된 Actions 정보 캐싱
- 최근 Workflow Runs 중심 조회
- 미확정 Actions 도넛은 화면에 보이는 실행에만 CSS 회전을 적용. 숨김 탭·화면 밖·완료 상태에서는 회전을 중단하며 동작 줄이기 설정을 따름. 애니메이션 때문에 DAG 전체를 다시 그리거나 API를 추가 조회하지 않음

`angular/angular`처럼 큰 저장소에서도 기본 탐색 성능이 크게 저하되지 않아야 합니다.

WebGL이나 새로운 그래프 라이브러리로 변경하지 않습니다.

## 14. 제외 사항

이번 작업에서는 다음을 구현하지 않습니다.

- GitHub Actions 직접 실행·취소·재실행
- Job별 로그 및 Step 상세 조회
- 실제 Deployment 상태 추적
- 외부 CI 서비스 연동
- 별도 Actions 대시보드
- Actions 전용 갱신 주기 설정
- 브라우저 알림 및 소리
- WebSocket·Webhook 서버
- 서버 측 데이터베이스
- 3D·WebGL 렌더링
- 복잡한 애니메이션

## 16. Codex 작업 지침

기존 GitStream 구현과 `docs/specification.md`를 먼저 확인합니다.

이번 명세는 기존 기본 그래프 기능을 대체하지 않고 확장하는 작업입니다.

가능하면 기존 API 클라이언트, 데이터 모델, 자동 갱신 로직, Canvas 렌더러 및 캐시를 재사용합니다.

자동 갱신이 아직 구현되지 않았다면 본 명세에 따라 함께 구현합니다.

### 권장 구현 순서

1. 공통 Polling 및 자동 갱신 설정
2. 브랜치 변경 감지와 커밋 증분 조회
3. 스크롤 위치 유지 및 최신 이력 자동 추적
4. 태그·릴리즈 API 조회 및 아이콘 표시
5. 최근 Workflow Runs 일괄 조회
6. Job 합산 진행률 및 최종 상태 표시
7. 공통 자동 갱신에 메타데이터 연동
8. PAT 권한 안내 수정
9. 테스트·빌드·성능 검증

### 개발 원칙

- 요청과 관계없는 리팩터링은 하지 않습니다.
- 공통 로직으로 통합할 수 있는 코드는 재사용합니다.
- 불필요한 라이브러리를 추가하지 않습니다.
- 오류를 조용히 무시하지 않습니다.
- GitHub 공식 API 문서를 우선 확인합니다.
- 커밋 메시지는 기존 GitMoji 형식을 사용합니다.
- 명시적 요청 없이 PR 생성·병합 및 배포를 수행하지 않습니다.

구현이 끝나면 변경 사항, 테스트 결과, API 호출 전략, 알려진 제약을 간결하게 보고합니다.

## 17. 구현 범위와 캐시 정책

- 하나의 갱신 루프를 사용하며, 수동 갱신과 주기 갱신은 중복 실행하지 않습니다. 숨김 탭·오프라인에서는 일시 중지하고 Rate Limit의 재시도 시각을 따릅니다.
- 브랜치 목록은 한 주기에 최대 3페이지씩 이어서 확인합니다. 전체 목록을 확인하기 전에는 삭제를 확정하지 않습니다. 삭제된 참조의 HEAD 추적은 종료하고, 공유 커밋과 관계를 확정하지 못한 기존 이력은 유지합니다.
- 이미 받은 커밋 객체와 고정 SHA의 조회 페이지를 재사용합니다. 메타데이터만 바뀌면 DAG 레이아웃과 스크롤 좌표를 유지합니다.
- 경과 시간은 기존 실행의 `run_started_at`부터 계산하며 완료된 실행은 마지막 API 상태 갱신 시각인 `updated_at`을 종료 기준으로 사용합니다. 시각이 누락되거나 잘못된 경우 `—`로 표시합니다. 진행 중인 상세 화면에서만 로컬 시계를 갱신하며 추가 API 요청을 보내지 않습니다.
- 조회 실패와 부분 페이지는 삭제나 데이터 부재의 증거로 사용하지 않습니다. 토큰의 localStorage 저장은 사용자가 확인한 기존 정책을 유지합니다.
- 캐시는 현재 저장소·토큰 세션의 메모리에만 유지합니다. 실제 대규모 저장소의 장시간 실측과 API 요청 횟수 계측은 이번 검증 범위에 포함하지 않았습니다.

- 부분 이력의 캐시 보존 정책은 유지하되 `Partial history` 상태 문구와 일반 갱신 시각의 부분 이력 안내 툴팁은 표시하지 않습니다.

- 커밋 상세 표시 여부와 그래프 선택은 동일한 선택 커밋 상태를 사용합니다. 상세 닫기 시 선택과 선택한 메타데이터 조회 대상을 해제하며, 완료 전인 조회 결과는 캐시에 보관하고 닫힌 상세를 다시 선택하지 않습니다.
